# データベース設計方針

本プロジェクト「X-Clone」では、大規模SNSという要件（大量のリアルタイムデータ、スクレイピング対策、堅牢なデータ整合性）を満たすため、Prismaを用いたデータベース設計において以下の3つの基本方針を採用しています。

---

## 1. 主キー設計 (CUIDv2)

すべてのテーブルの主キー（`id`）には、連番（Auto Increment）やUUIDv4ではなく、**CUIDv2**（Collision Resistant Unique Identifier version 2）を採用します。

### 採用理由
- **スクレイピングと推測の防止**: 連番IDの場合、URLから「1日に何人が登録したか」「何件の投稿があるか」といったビジネス指標が他社に筒抜けになり、Botによるデータ収集の標的になります。CUIDv2はランダムで予測不可能なためこれを防ぎます。
- **URLセーフ**: UUID（例: `123e4567-e89b-...`）は長くハイフンを含むため、URLパラメータとして不格好ですが、CUIDv2（例: `tz4a98xxat96iwhqjl...`）は短くURLに適しています。
- **衝突耐性**: 将来的にシステムが分散環境（マイクロサービスなど）に移行しても、IDが被る（衝突する）リスクが極めて低い設計になっています。

### 実装方法
Prismaスキーマでは `@default(cuid())` を指定するだけで、自動的にCUIDv2が生成されます。

```prisma
model User {
  id String @id @default(cuid())
  // ...
}
```

## 2. ページネーション (カーソルベース)

タイムラインのような「無限スクロール」を実装するデータ取得には、オフセットベースではなく**カーソルベース・ページネーション**を採用します。

### オフセットベースの課題（不採用の理由）
「最初から20件飛ばして、次の10件を取得する（`OFFSET 20 LIMIT 10`）」という手法です。
- **データのズレ**: ユーザーが次のページを読み込む間に新しい投稿が追加されると、既存の投稿が押し出され、同じ投稿が2回表示される（重複）か、見逃しが発生します。
- **パフォーマンス低下**: データ量が数百万件規模になると、データベースは飛ばす分のレコード（20件）も内部で数え直す必要があり、奥のページに行くほど劇的にレスポンスが遅くなります。

### カーソルベースの利点
「最後に見えた投稿ID（カーソル）を基準に、それより古いものを10件取得する」という手法です。
- **リアルタイム性に強い**: 基準となるIDの「次」から取得するため、新規投稿が何件増えてもタイムラインが一切ズレません。
- **高速（O(1)に近い）**: 指定されたIDにインデックスを使って直接ジャンプするため、100万件のデータがあっても取得速度が常に一定です。

### 実装方法
Prismaの `cursor` と `take` オプションを組み合わせて実装します。

```typescript
// 投稿取得ロジックの例
const posts = await prisma.post.findMany({
  take: 10,
  skip: cursorId ? 1 : 0, // カーソル自体を含めないために1件スキップ
  cursor: cursorId ? { id: cursorId } : undefined,
  orderBy: { createdAt: 'desc' },
});
```

## 3. データの削除 (論理削除)

ユーザーデータや投稿データは、データベースから完全に消し去る物理削除（`DELETE`）ではなく、削除日時を記録する**論理削除**（Soft Delete）を採用します。

### 採用理由
- **リレーション整合性の保持**: ユーザーを物理削除すると、そのユーザーが行った「いいね」や「リプライ」のデータと不整合が起き、アプリケーション全体でクラッシュの原因となります。
- **誤操作からの復旧**: ユーザーからの「誤ってアカウントを消してしまった」という問い合わせに対応可能です。
- **分析・監査**: 過去の利用履歴としてデータを保持できるため、不正行為の調査などに役立ちます。

### 実装方法
すべての主要テーブルに `deletedAt` カラムを追加します。

```prisma
model Post {
  id        String    @id @default(cuid())
  content   String
  deletedAt DateTime? // NULLの場合は有効、日時が入っていれば削除済み
}
```

データ取得時は、必ず `deletedAt: null` を条件に含めてフィルタリングを行います。

```typescript
// 有効な投稿のみを取得
const activePosts = await prisma.post.findMany({
  where: {
    deletedAt: null,
  },
});
```
